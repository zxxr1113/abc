AVX-512 仿真后端：可行性分析与设计方案
0. 执行摘要（先说结论）
经过对你当前分支 src/proof/cec/cecClass.c:668、src/aig/gia/giaSimBase.c:93 和 src/proof/cec/cecCexLift.c:125 的逐函数分析，我建议不要立即做 AVX-512，理由是三个层面同时不利：

硬件层：你这台 i9-13900HX (Raptor Lake) 没有 AVX-512。Intel 客户端 CPU 自 Alder Lake 起 AVX-512 已被 fuse off,Raptor Lake 完全不支持。当前 /proc/cpuinfo 里只有 avx avx2 avx_vnni,无 avx512f。这意味着你无法在本机测量自己的设计——所有度量必须依赖远程 Xeon SPR 或 AMD Zen4 服务器,你的迭代周期会被严重拉长。
算法层:scorr 用的仿真核心是 cecClass.c:Cec_ManSimSimulateRound,不是 giaSimBase.c::Gia_ManSimPatSim。它的特征是每节点内层循环极短(nWords=31,32-bit word → 124 字节 ≈ 2 个 zmm 寄存器),且每节点有非平凡的引用计数与等价类簿记开销(Cec_ManSimSimRef/Deref、Gia_ObjIsTail 分支、Cec_ManSimClassRefineOne)。Amdahl 之下,8× SIMD 宽度对单节点 inner loop 顶多带来 1.5–2× 仿真核加速。
整体 wall-time 占比:你 optimization_way.md 里估的"仿真占 30–50%"是上限,我下面会论证真实占比可能更低。整体 scorr 端到端加速 ≤ 1.3×,投入产出比劣于 CEX lifting / UNSAT-core 调度等其它方向。
更重要的:AVX2 (256-bit) 路径在你本机就能跑,能拿到 AVX-512 理论收益的 70–80%,而代码与设计成本几乎相同。如果一定要做 SIMD 化,正确的目标是 AVX2 优先 + AVX-512 作为可选 zmm 后端,不是 AVX-512 优先。

下文按"为什么"→"如果坚持要做的设计方案"→"隐藏 bug 清单"→"替代路径"四部分展开。

2. 算法可行性:scorr 仿真的真实形状
2.1 scorr 用的不是 giaSimBase.c
调用链:Cec_ManResimulateCounterExamples → cecCorr.c:569 → Cec_ManSeqResimulate → cecSeq.c:166 → Cec_ManSimSimulateRound → cecClass.c:668。

这个 Cec_ManSimSimulateRound 才是 scorr 的真热点。它有几个显著特征:


// cecClass.c:739, 内层 AND 仿真
if ( Gia_ObjFaninC0(pObj) ) {
    if ( Gia_ObjFaninC1(pObj) )
        for ( w = 1; w <= p->nWords; w++ )
            pRes[w] = ~(pRes0[w] | pRes1[w]);
    else
        for ( w = 1; w <= p->nWords; w++ )
            pRes[w] = ~pRes0[w] & pRes1[w];
} else { ... }
数据宽度:unsigned* = 32-bit word,默认 nWords=31 → 单节点 124 字节(参见 cecCore.c:74)。
每节点循环长度:31 次 32-bit AND/OR/NOT。AVX-512 一条 _mm512_and_si512 处理 64 字节 → 整个节点 2 条 zmm + 1 个 scalar tail(剩 60 字节)。
重要:每节点不仅有这个内层循环,还有非循环开销:Cec_ManSimSimRef(p, i) 引用计数(可能触发 relink)、Cec_ManSimSimDeref ×2、Gia_ObjIsConst/IsClass/IsTail 分支、若是 tail 还要 Cec_ManSimClassRefineOne(O(类大小) 的细化)。
2.2 Roofline 估算
每节点内层循环的 arithmetic intensity:

124 字节 load(2 个 fanin × 124 + 自身写 124 = 372 字节内存流量)
31 个简单逻辑 op
AI ≈ 31 / 372 ≈ 0.08 ops/byte
i9-13900HX P-core L1 带宽 ~256 GB/s,SPR Xeon AVX-512 L1 带宽 ~400 GB/s,但 AIG 节点遍历是指针追踪(Gia_ObjFaninId0(pObj, i) 算 fanin 索引,然后跨 GIA 数组跳跃 load)→ 实际 working set 大概率在 L2/L3,带宽降到 80–150 GB/s。

这意味着仿真核是 memory-bound,不是 compute-bound。SIMD 宽度从 64 → 512 对 compute throughput 提升 8×,但对 DRAM/L3 带宽提升 0×。预期的真实加速:1.5–2.5×(缓存命中好的中等电路) 到 1.1–1.3×(大型电路 working set 溢出 LLC)。

2.3 端到端 Amdahl
scorr 总时间分为:仿真(Cec_ManSimSimulateRound 累计) + SAT(cecSatG.c 等) + SRM 重建(Gia_ManCorrSpec*) + 杂项。社区公认的近似分布:

中型电路(~10⁵ 节点):仿真 15–25%,SAT 60–75%,其它 10–15%
大型电路(~10⁶):仿真 30–40%,SAT 50–60%,SRM 重建 10–20%
按你 optimization_way.md 写的 30–50% 上限,即使仿真核内做到 2× 提速:

30% × 0.5 (省一半) → 端到端 1.18× 加速
50% × 0.5 → 端到端 1.33× 加速
这是一个相当温和的回报,而你 CEX lifting 那一项预期 2–3×、UNSAT-core 调度预期 1.5–2×,投入产出比都更高。

2.4 CEX lifting 的 AVX 适配性反而更高
cecCexLift.c:TernaryBatch64 是另一个故事。它的特征:

每节点只持有 1 个 Word64(=64 个 trial 并行)
每个 batch 测试 ≤64 个 literal,通过 for ( i = 0; i < nLits; i += 64 ) 外层迭代(cecCexLift.c:241)
整图遍历开销在每个 batch 都重复一次
这里 AVX-512 价值更大:把每节点存储从 1× Word64 → 1× zmm(=8 个 Word64 = 512 trial),整图遍历次数从 ⌈nLits/64⌉ 降到 ⌈nLits/512⌉。如果典型 cube 大小 200 literals → 4 次 → 1 次,端到端 lifting 时间 3–4× 加速。

但 lifting 本身在 scorr 整体里的占比有多大?根据你 cex_lifting 分支已经做的 64× bit-parallel 优化,lifting 大概率已经 < 10% wall time → 即使再 4×,端到端 < 5% 收益。

结论:CEX lifting 内部不值得为 AVX-512 单独花预算,除非你有诊断显示 lifting 仍是热点。

3. 如果坚持要做:完整设计方案
(下面给出的是"假设你确实拿到了 AVX-512 服务器,且决定为长期部署投资"的方案。我不建议立刻动手实现。)

3.1 总体架构:三层抽象

┌─────────────────────────────────────────────────────────┐
│  Layer 3: 调用方 (cecClass.c, cecCexLift.c, giaSimBase.c)│
│            统一通过 Sim_BackendOps* 调度                 │
├─────────────────────────────────────────────────────────┤
│  Layer 2: SimVec 抽象类型                                │
│   - SimVec_t = { void* data; int nLanes; }              │
│   - SimVecOps = { and, or, not, xor, load, store, ... } │
├─────────────────────────────────────────────────────────┤
│  Layer 1: 后端实现                                       │
│   - sim_backend_scalar.c   (uint64_t,  64-bit lanes)    │
│   - sim_backend_avx2.c     (__m256i,  256-bit lanes)    │
│   - sim_backend_avx512.c   (__m512i,  512-bit lanes)    │
└─────────────────────────────────────────────────────────┘
为什么是 3 后端而不是 2 后端:你本机连 AVX-512 的 smoke test 都跑不了。AVX2 后端是你实际开发与回归测试的载体。AVX-512 是"产品交付时绑定到目标硬件"的可选最佳后端。Scalar 后端是 32-bit ARM/老 x86/CI 容器的兜底。

3.2 数据布局策略
关键决策:每节点的仿真数据是横向连续(同一节点的 nLanes 字节连续)还是纵向打包(同一 lane 跨节点连续)?

现状:横向。pSims + nWords*objId 是该节点的全部 word。Cache 局部性按节点。
AoS(横向)适合"按节点遍历,每节点做完整 bitwise 操作"——这正是 scorr 的访问模式 → 保持 AoS。
SoA(纵向)在跨节点求 reduction(比如全图 popcount)时更优,但 scorr 不做这个。
对齐:

当前 Vec_PtrAllocSimInfo 通过 ABC_ALLOC → malloc,glibc 给 16-byte 对齐。AVX-512 unaligned vmovdqu64 能跑,但跨 cache line load 罚 2× cycles。
方案:新增 Vec_PtrAllocSimInfoAligned(nLanes, alignment),内部 posix_memalign(64)(64 字节 = AVX-512 lane,也是 cache line)。不要用 aligned_alloc(C11 要求 size 是 align 倍数,可能踩坑)。
对每节点的 simulation buffer,在 nLanes 不是 64 字节倍数时强制 padding 到 64 字节边界,代价是每节点多用 ≤ 60 字节 → nWords=31 (124 B) 变 128 B,内存涨 3% → 可忽略。
反相边处理:

现状:用 pComps[2] = { 0, ~(word)0 } + Diff = pComps[FaninC] + XOR Diff 来反相,这是分支无关的(参见 giaSimBase.c:95),映射到 SIMD 直接是 _mm512_xor_si512(load, broadcast_diff)。无需额外设计。
cecClass.c 用了 4 路展开的 if (FaninC0) { if (FaninC1) ... },该模式映射 SIMD 时应该重写为 XOR-mask 形式(像 giaSimBase.c 那样),避免在 SIMD 后端里展开成 4 个内核。重写一次,3 个后端共享同一份代码骨架。

3.4 512-bit 带宽用法:不要只是更宽,要更"好用"
你 prompt 里点出了关键问题。我的具体建议:

场景	64-bit 行为	512-bit 应该这样用
scorr 主仿真	nWords=31 个 32-bit word	直接展宽到 nLanes=64 个 32-bit word(=2 zmm),即每轮 2048 bit/节点。Cost: 内存 2.06×,仿真核加速 ~6× → 净加速 ~3×
scorr 反例增量	1 word/节点	64 个反例 lifting variants 全部塞进 1 zmm 节点字
CEX lifting	nLits/64 batches	nLits/512 batches → 整图遍历次数 8× 减少
主仿真的"宽度选择"是有 trade-off 的:

更宽 → 单轮捕获更多等价对划分(收益)
更宽 → 单轮内存占用更大,LLC miss 增加(成本)
更宽 → SAT 调用频率不变,但每次 SAT 之间的"仿真 + SRM rebuild"周期更长 → 反例消化更慢(成本)
经验法则:仿真宽度让等价类划分饱和后就够了。从 64 → 256 → 512 → 1024 通常呈对数收益(收益减半率 ≈ 50%)。我建议把 nLanes 做成参数,默认 256(AVX2 = 1 ymm 满,AVX-512 = 半 zmm),让用户用 -W 调到 512/1024。不要默认就 1024——大电路上 LLC miss 抵消 SIMD 收益。

4. 隐藏 bug 与陷阱清单
按踩坑概率排序(高到低):

4.1 nWords=31 的尾部处理(高概率)
nWords=31 个 32-bit word = 124 字节。AVX-512 zmm = 64 字节 = 16 个 32-bit。31 mod 16 = 15 → 1 个完整 zmm + 15 个 32-bit 尾巴。

错法:for (i=0;i<nWords/16;i++) zmm_op(...); for (;i<nWords;i++) scalar_op(...); —— 看似没错,但尾部那 15 个 32-bit 紧跟着前一节点的数据(因为 AoS 布局是 data[obj*nWords + w])。如果你按 64 字节读,会越界读到下个节点的前 4 字节。在 AlignedAlloc + padding 之前,这是 segv 风险。

正确做法:padding 每节点到 SIMD 倍数,或用 _mm512_maskz_loadu_epi32(mask, ptr) 加 mask 屏蔽尾部。我推荐 padding,运行时分支更少。

4.2 32-bit vs 64-bit lane 语义混淆
scorr 用 unsigned*(32-bit),lifting 用 Word64(64-bit),giaSimBase.c 用 word(64-bit)。SIMD 对纯 bitwise(AND/OR/XOR/NOT)无所谓 lane 宽度——结果一致。但:

_mm512_shuffle_epi32 等需要指定 lane 宽度的 op 会出错。
popcount(用于 Abc_TtCountOnesVec)在 32-bit / 64-bit lane 上结果一致(只要总位数一致),但 AVX-512 popcount 用 _mm512_popcnt_epi64(VPOPCNTDQ 扩展,需要 ICX/SPR)→ Skylake-X / Cascade Lake 不支持,需要 fallback 到 Harley-Seal 软件 popcount。
4.3 AVX-512 downclocking(中等概率)
Skylake-X / Cascade Lake / Ice Lake 触发 AVX-512-heavy(license 2)会让核心降频 200–500MHz。Sapphire Rapids / Emerald Rapids / Granite Rapids 这块改进很多,但要在客户机上测才知道。症状:512-bit 版本比 256-bit 慢 5–15%,整体性能不增反降。

防御:别在小工作负载里(<10ms)进 AVX-512;短调用走 AVX2。用 turbostat 监 freq 来诊断。

4.4 内存分配不对齐(中等概率)
Vec_PtrAllocSimInfo 当前不保证 64 字节对齐。如果你用 _mm512_load_si512(对齐版),会 #GP fault。要么换 _mm512_loadu_si512(2× 慢但安全),要么在 Vec_PtrAllocSimInfo 路径上彻底改对齐。我推荐改对齐 + 用对齐 load。但要审计所有调用方,有些地方用 Vec_WrdEntryP 拿到中间偏移,可能不在 64 字节边界——这种情况要么 padding,要么强制走 unaligned。

4.5 SRM 重建后的 reslice(低概率但麻烦)
scorr 每过几轮会 rebuild SRM(cecCorr.c 中 Gia_ManCorrSpec*)。新 SRM 的 Gia_ManObjNum 变化 → 仿真 buffer 要 realloc。如果新 buffer 没保持 64 字节对齐 → 跑到一半 segv。

4.6 代码复用 vs 4 个 fanin-complement 分支(低概率,但 ugly)
cecClass.c:736 的 4 路 if-else 展开,直接复制 4 份 SIMD 代码会维护爆炸。建议:统一改写为 pRes[w] = (pRes0[w] ^ Diff0) & (pRes1[w] ^ Diff1),跟 giaSimBase.c:107 一致。这是个改 cecClass.c 算法的 PR,要单独做并 regression test,不能跟 SIMD 改一起上。否则你不知道是 SIMD 引入 bug 还是这次改写引入 bug。

4.7 dispatch 函数指针的 inlining 损失
通过 g_pSimBackend->and_inplace(...) 调用 inner kernel,编译器无法 inline,每节点循环要付 1 次间接 call 开销(~2ns)。在 short loop 上(每节点 2 zmm 操作 ≈ 1ns)是 100% overhead。

解法:dispatch 应该在函数级(Cec_ManSimSimulateRound_AVX512)而不是操作级(每个 AND 一次 call)。用宏或 inline 函数把整个 simulation round 实例化 3 份,在 Cec_ManSimSimulateRound 顶层根据 backend 跳转到对应版本。代码 3× 但性能正确。

5. 替代路径(我的实际推荐)
按投入产出排序:

A. 先做 32-bit → 64-bit 数据宽度提升(1–2 天)
cecClass.c:Cec_ManSimSimulateRound 用 unsigned* 是历史包袱(早期 ABC 还在 32 位机上跑)。直接改成 word*(uint64_t)就免费 2×——无 SIMD,无对齐问题,无 CPUID dispatch。

风险:Vec_PtrAllocSimInfo 的 word size 假设、Cec_ManSimCompareConst/Equal 的 word size 假设、引用计数管理(Cec_ManSimSimRef/Deref)。中等改动,但局部。

预期:仿真核 1.8–2.0×,端到端 1.2–1.4×。比 AVX-512 投入小 5×、收益持平。

B. 然后做 AVX2 后端(1 周)
在 64-bit 化之后,再加 AVX2。256-bit = 4 × uint64_t = 一条 _mm256_and_si256。Haswell 以来全 x86 都支持,你本机能跑能测。

预期:仿真核再 1.6–2.0×,叠加 A 之后端到端 1.5–1.8×。

C. AVX-512 留给"只在产品环境部署"的目标硬件(2–3 周)
只在你确认要部署的目标机器(SPR Xeon / Genoa)上做,且做的时候 backend dispatch 框架已经在 (B) 里就绪,只需要新增一个 sim_backend_avx512.c。

如果连 (A) 都没做,直接做 AVX-512 是反向最优:你会在最复杂的路径上撞最简单的 bug,且测不了。

D. 你 optimization_way.md 里其它方向的优先级
按 ROI:CEX lifting 完善 > UNSAT-core 调度 > 64-bit widening (A) > AVX2 (B) > PDR lemma 注入 > AVX-512 (C)。

0. 设计原则与边界
在动笔之前先把"非侵入"的边界量化,避免后面写得越来越大:

/* 从 unsigned* (32-bit, 调用方已有的指针类型) 不对齐加载一个 Sim_Vec_t */
#if   defined(SIM_BACKEND_AVX2)
  #define SIM_VLOAD(p32)            _mm256_loadu_si256((const __m256i*)(p32))
  #define SIM_VSTORE(p32, v)        _mm256_storeu_si256((__m256i*)(p32), (v))
  #define SIM_VAND(a, b)            _mm256_and_si256((a), (b))
  #define SIM_VOR(a, b)             _mm256_or_si256((a), (b))
  #define SIM_VXOR(a, b)            _mm256_xor_si256((a), (b))
  #define SIM_VANDNOT(a, b)         _mm256_andnot_si256((a), (b))   /* (~a)&b */
  #define SIM_VBCAST_ZERO()         _mm256_setzero_si256()
  #define SIM_VBCAST_ONES()         _mm256_set1_epi64x((long long)~0ULL)
  #define SIM_VBCAST_FROM_BIT(b)    ((b) ? SIM_VBCAST_ONES() : SIM_VBCAST_ZERO())

#elif defined(SIM_BACKEND_SCALAR64)
  /* memcpy-based unaligned load 是首选:
     1) 不依赖编译器 -fno-strict-aliasing;
     2) 现代 gcc/clang 把 memcpy(8) 优化成单条 mov;
     3) 不会触发 UBSan 的 misaligned-pointer warning. */
  static inline uint64_t  Sim__load_u64 (const void* p) {
      uint64_t v; memcpy(&v, p, sizeof v); return v;
  }
  static inline void      Sim__store_u64(void* p, uint64_t v) {
      memcpy(p, &v, sizeof v);
  }
  #define SIM_VLOAD(p32)            Sim__load_u64((const void*)(p32))
  #define SIM_VSTORE(p32, v)        Sim__store_u64((void*)(p32), (v))
  #define SIM_VAND(a, b)            ((a) & (b))
  #define SIM_VOR(a, b)             ((a) | (b))
  #define SIM_VXOR(a, b)            ((a) ^ (b))
  #define SIM_VANDNOT(a, b)         ((~(a)) & (b))
  #define SIM_VBCAST_ZERO()         ((uint64_t)0)
  #define SIM_VBCAST_ONES()         (~(uint64_t)0)
  #define SIM_VBCAST_FROM_BIT(b)    ((b) ? ~(uint64_t)0 : (uint64_t)0)

#elif defined(SIM_BACKEND_SCALAR32)
  /* 与 scalar64 同形式,uint32_t 版本 */
  ...
#endif

/* 对调用方暴露:每节点 unsigned 字数 → 后端向量数 */
#define SIM_NVEC_FROM_NWORDS32(nWords32) \
    ( ((nWords32) * 4) / SIM_VEC_BYTES )
#define SIM_NTAIL_BYTES_FROM_NWORDS32(nWords32) \
    ( ((nWords32) * 4) % SIM_VEC_BYTES )
这是非侵入设计的关键:SIM_VLOAD 接受 unsigned*(=uint32_t*,正是 cecClass.c 现有数据类型)并 memcpy 重解释。调用方一行代码都不用改 alignment。

#define SIM_KERNEL_FN(name, suffix)  SIM_KERNEL_FN_(name, suffix)

/* Per-AND-node 内层逻辑:这是要被向量化的核心 30ns 路径 */
static void
SIM_KERNEL_FN(AndNode, SIM_BACKEND)
( unsigned * restrict pRes,        /* 输出:nWords32 个 uint32_t */
  const unsigned * restrict pRes0,
  const unsigned * restrict pRes1,
  int compl0, int compl1,
  int nWords32 )
{
    Sim_Vec_t m0 = SIM_VBCAST_FROM_BIT(compl0);
    Sim_Vec_t m1 = SIM_VBCAST_FROM_BIT(compl1);
    int nVec    = SIM_NVEC_FROM_NWORDS32(nWords32);
    int tailBytes = SIM_NTAIL_BYTES_FROM_NWORDS32(nWords32);
    int v;

    for ( v = 0; v < nVec; v++ ) {
        const unsigned * p0 = pRes0 + v * (SIM_VEC_BYTES / 4);
        const unsigned * p1 = pRes1 + v * (SIM_VEC_BYTES / 4);
        unsigned       * pd = pRes  + v * (SIM_VEC_BYTES / 4);
        Sim_Vec_t a = SIM_VXOR(SIM_VLOAD(p0), m0);
        Sim_Vec_t b = SIM_VXOR(SIM_VLOAD(p1), m1);
        SIM_VSTORE(pd, SIM_VAND(a, b));
    }

    /* 尾巴:用 scalar32 收尾,无论后端如何 */
    if ( tailBytes ) {
        int wOff = nVec * (SIM_VEC_BYTES / 4);
        int wEnd = nWords32;
        uint32_t mm0 = compl0 ? ~0u : 0u;
        uint32_t mm1 = compl1 ? ~0u : 0u;
        int w;
        for ( w = wOff; w < wEnd; w++ )
            pRes[w] = (pRes0[w] ^ mm0) & (pRes1[w] ^ mm1);
    }
}

3. 64-bit widening 与 AVX2 的统一抽象
这是 (a) 与 (b) 合并的关键。

3.1 内存与指针重解释(零侵入)
调用方(cecClass.c)给我们的是 unsigned * pRes,长度 nWords 个 uint32_t,glibc 16-byte 对齐(ABC_ALLOC → malloc)。

我们的处理:

不要求对齐:统一用 unaligned load(AVX2 上 _mm256_loadu_si256,scalar 上 memcpy(8))。
不改 nWords 语义:对调用方 nWords 仍是 32-bit word 数;我们内部按 nVec = (nWords*4) / SIM_VEC_BYTES 算向量数。
尾巴:(nWords*4) % SIM_VEC_BYTES != 0 时跑 scalar32 收尾(见 §2.3)。
nWords=31 默认值的实际拆分:

Backend	主循环 vec 数	尾巴 byte 数	尾巴 uint32 数
scalar32	31	0	0
scalar64	15	4	1
avx2	3	28	7
AVX2 的尾巴占 22%(7/31),不忽略。两种处理:

尾巴用 SSE2(16-byte)而不是 scalar32:__m128i _mm_loadu_si128,4 个 uint32 一组 → 7 字 = 1 SSE + 3 scalar。代码复杂。
直接 7 次 scalar32:简单,损失约 22% × (1-AVX2加速比) 的潜在加速。
我推荐 (2),代码可读性远好于 (1),损失可接受。如果将来 profile 显示尾巴是热点再上 SSE。

3.2 内存别名安全性
把 unsigned* 当 __m256i* 用,在 C 标准下是 strict aliasing 违例(__m256i 与 unsigned 不是兼容类型族)。然而:

gcc/clang 把 __m256i 标为 may_alias 类型,加载/存储不会触发未定义行为。
用 _mm256_loadu_si256 而不是 *(__m256i*)p 是关键(intrinsic 内部已声明 may_alias)。
scalar64 路径用 memcpy(8) 完全合规,无 aliasing 问题。
scalar32 路径就是原代码,无问题。
→ 不会引入 UB,前提是 LOAD/STORE 一律走 intrinsic 或 memcpy,禁止裸的 *(__m256i*)p 写法。这一点要在代码评审 checklist 里写死。

3.3 64-bit widening 的"自动落地"
这套设计的好处:(a) 64-bit widening 是 (b) AVX2 的副产品。

启用 scalar64 后端 = 完成方向 (a) 的全部目标
启用 avx2 后端 = 完成方向 (b)
两者共享同一份 sim_accel_kernel.inc,不需要写两遍
实施顺序:

先把 sim_accel/ 目录建起来,只激活 scalar32 + scalar64。这阶段验证宏层 + 影子校验 + 集成路径。
加 avx2 后端文件,纯加法,不动其它。

7. 影子校验 (sim_accel_check.c)
设计目标:在 --check-shadow 开关下,每次 fast kernel 运行后立即用 scalar32 重算并 diff,定位首个 mismatch 节点。


/* sim_accel.h */
void Sim_AccelEnableShadow(Sim_AccelCtx_t * pCtx, int fEnable);

/* and_kernel 实现示意(在 dispatch 层包一层) */
void Sim_AccelAndKernel(Sim_AccelCtx_t * pCtx, unsigned * pRes, ...) {
    if ( pCtx->fShadow ) {
        /* 1. 把 pRes 现状备份(它会被覆写) */
        unsigned shadowOut[MAX_NWORDS_INLINE];   /* 或动态 alloc 存到 ctx */
        int n = pCtx->nWords32;

        /* 2. 用 scalar32 后端跑一次到 shadow buffer */
        g_BackendScalar32.and_kernel(shadowOut, pRes0, c0, pRes1, c1, n);

        /* 3. 跑 fast 后端到 pRes */
        pCtx->ops->and_kernel(pRes, pRes0, c0, pRes1, c1, n);

        /* 4. diff */
        for ( int w = 0; w < n; w++ ) {
            if ( pRes[w] != shadowOut[w] ) {
                pCtx->shadowMismatch++;
                if ( pCtx->shadowMismatch == 1 ) {
                    /* 第一次 mismatch:固化全部输入与输出,稍后 dump */
                    Sim_AccelShadow_CaptureFirst(pCtx, pRes, shadowOut, ...);
                }
            }
        }
    } else {
        pCtx->ops->and_kernel(pRes, pRes0, c0, pRes1, c1, pCtx->nWords32);
    }
    pCtx->stats.nKernelCalls++;
    pCtx->stats.nGateBitsAnd += (uint64_t)pCtx->nWords32 * 32;
}
触发方式:命令行 &scorr -X(新增 -X 标志)或环境变量 ABC_SIM_SHADOW=1。在 &scorr 入口看到任一开启,调 Sim_AccelEnableShadow(p->pAccel, 1)。

预期 cost:开启 shadow 时仿真慢 ~3×(标量重跑 + diff 扫描)。开发期使用,生产关闭。

校验粒度:per-kernel-call,而不是 per-round-end。这意味着第一个 SIMD bug 当场被 catch,不会传染到下游 class refinement。

额外的 round-end 校验(可选):在 Cec_ManSimSimulateRound 末尾对 pAig->pReprs[] 做 FNV-1a 哈希,并且和单独跑 ABC_SIM_BACKEND=scalar32 的 hash 比对。这是端到端正确性证据。两种校验独立,都加。

8. 度量埋点 (sim_accel_stats.c)

/* === scalar32 inline kernel === */
static inline void cec__and_scalar32(unsigned*pd,const unsigned*p0,int c0,
                                     const unsigned*p1,int c1,int n) {
    uint32_t m0 = c0?~0u:0u, m1 = c1?~0u:0u;
    int w; for (w=0;w<n;w++) pd[w] = (p0[w]^m0)&(p1[w]^m1);
}
static inline void cec__co_scalar32(unsigned*po,const unsigned*pi,int c0,int n) {
    uint32_t m = c0?~0u:0u;
    int w; for (w=0;w<n;w++) po[w] = pi[w]^m;
}

/* === scalar64 inline kernel ===  (同理,8字节 stride + 4字节尾巴) */
static inline void cec__and_scalar64(unsigned*pd,const unsigned*p0,int c0,
                                     const unsigned*p1,int c1,int n) {
    uint64_t m0 = c0?~(uint64_t)0:0, m1 = c1?~(uint64_t)0:0;
    int nv = (n*4)/8, v;          /* 64-bit vec count */
    for (v=0; v<nv; v++) {
        uint64_t a,b; memcpy(&a,p0+v*2,8); memcpy(&b,p1+v*2,8);
        uint64_t r = (a^m0)&(b^m1); memcpy(pd+v*2,&r,8);
    }
    if ((n*4)%8) {            /* 1 uint32 tail when n is odd */
        uint32_t mm0 = c0?~0u:0u, mm1 = c1?~0u:0u;
        pd[n-1] = (p0[n-1]^mm0) & (p1[n-1]^mm1);
    }
}

inline kernel 写在 cecClass.c 而不是 sim_accel/:因为模板需要它们 static inline 在同一 TU 才能保证 inline 进 round 函数。sim_accel/ 现有 _kernel.inc 保留作为 shadow check 路径与未来批处理 API 的后端,不浪费。

#pragma GCC target("avx2") 范围:只包住 cec__*_avx2 静态 inline 函数 + avx2 模板实例化 #include 块。不能包住 Cec_ManSimSimRef/Deref/ClassRefineOne 的调用本身——这些是从其他 TU 链接进来的普通函数,从 avx2-targeted 函数调过去是合法 ABI,只是 GCC 不会跨 target 内联(我们也不希望内联它们)。

Sim_BackendOps_t::id 用于 dispatch:不能用编译时 #ifdef,因为我们要保持单二进制可移植性。CPUID 在 Sim_AccelGlobalInit 已经选好了。

shadow check 路径仍走旧 op-level kernel:Sim_AccelEnableShadow 触发时,把 ctx 标记一下,模板 entry 处分支到旧的 Sim_AccelAndKernel(per-call dispatch)。这条路径 3× 慢但用于校验,不要求快。

为什么不会改变正确性:

nWords 是「随机仿真位数除以 32」——更多位只是更多区分能力,不改变等价类的可证安全性
cecClass.c:50/80/110/140(Cec_ManSimCompareConst/Equal*)都参数化在 nWords 上,自适应
cecClass.c:680(pScores 分配 32*nWords)、cecClass.c:539/569(32*nWords 上界)都自适应
ClassesPrepare 的 1→3→7→15→31 序列怎么办?
cecClass.c:892-904 的 do { … p->nWords = 2*p->nWords + 1; } while (p->nWords <= pPars->nWords); 在 pPars=16 时停在 nWords=15 一轮,跟现在完全一样(只是 ClassesRefine 阶段从 nWords=15 变成 nWords=16)。Prepare 阶段 4 轮 × 5 步 = 20 轮,Refine 阶段才是热点(nRounds 默认 15,nFrames 增大后还多),所以 B1 命中的就是热点。

B2 作为可调档位
把 nWords 提到 32 = 4 个 ymm vec,无 tail。仿真位数翻倍:每 round 处理 1024 bit/node 而不是 512 bit。优点:更多 refinement 信号,每 round 价值更高;缺点:LLC 压力增大,内存上升 ~6%。

实施:加一个 CLI 选项 &scorr -W 32 或者直接调默认。先在大电路上 A/B,再决定是否改默认。

B3(可选,纯净路径)
如果 B1/B2 的「nWords 暴露给所有调用方」让你不舒服,可以做内部 padding:


/* cecMan.c — Cec_ManSimStart */
p->nWordsPadded = (pPars->nWords + 7) & ~7;   /* round up to 8 */
/* freelist stride 改用 nWordsPadded+1,数据有效长度 nWords */
然后 Cec_ManSimMemRelink 与 Cec_ManSimSimRef 的 stride 计算改用 nWordsPadded+1,所有 Compare* 仍读 p->nWords。Inner kernel 跑满 nWordsPadded words(读越界数据是 0 或随机,无影响——因为 Compare 只看前 nWords 个)。

B3 的风险:

Compare* 用 nWords 但内存有 nWordsPadded 个,padding 字节里是垃圾——Cec_ManSimHashKey(cecClass.c:366)会哈希全部 nWords 字,如果有人改成哈希 nWordsPadded 字会出 bug。只要全程区分 nWords(语义)和 nWordsPadded(布局),没问题。
Cec_ManSimCreateInfo 写 CI sim info 时也只写前 nWords 字,padding 区是未初始化内存——上次循环留下的旧值。AND kernel 会拿这些未初始化字算结果,但 Compare 只看前 nWords 字,所以结果无影响,但 valgrind 会噪声。要么 Cec_ManSimSimRef 后面把 padding 字清零(每节点多写 1-7 个 0,可忽略),要么接受 valgrind 假阳性。
我的建议:先做 B1(1 行,zero risk),实测后再考虑 B2,B3 留作未来。
