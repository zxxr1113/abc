&scorr / scorr SAT 引擎深度审计报告
1. 增量机制审计
调用栈精确分析
&scorr 的 CBS 路径（fUseCSat=1，默认路径）：


Cec_ManLSCorrespondenceClasses()         [cecCorr.c:935]
  └─ for r in range(100000):             [cecCorr.c:1001]
       pSrm = Gia_ManCorrSpecReduce()    ← 每轮重建 SRM
       Cbs_ManSolveMiterNc(pSrm, ...)   [giaCSat.c:1037]
         └─ p = Cbs_ManAlloc()          ← 每轮分配全新 CBS 实例
              for each CO in SRM:
                Cbs_ManSolve(p, CO)     ← 完全独立调用，无状态继承
                  CancelUntil(0)        ← 每次求解后清空 trail/clauses
关键发现：CBS 模式下没有任何增量机制。每轮创建全新 Cbs_Man_t，每次 Cbs_ManSolve 调用结束时 Cbs_ManCancelUntil(p, 0) 将 pProp.iTail=0、pJust.iTail=0、pClauses.iTail=1 全部重置（giaCSat.c:960-962）。CBS 对每个 SRM 输出完全从零开始，没有学到的任何子句被继承。

&scorr 的非 CBS 路径（fUseCSat=0）：


Cec_ManSatSolveMiter(pSrm, ...)         [cecSolve.c:1070]
  └─ p = Cec_ManSatCreate()             ← 一轮 ONE 个 MiniSAT 实例
       for each CO in SRM:
         Cec_ManSatCheckNode(p, CO)     [cecSolve.c:470]
           ├─ Cec_CnfNodeAddToSolver()  ← 累积编码 CNF（如已编码则跳过）
           └─ sat_solver_solve(&Lit,…)  ← 单字面量假设
               if UNSAT:
                 sat_solver_addclause(&neg_Lit) ← 把否定作为永久单元子句写入
这才是真正的增量：第 i 个 CO 被证明后，其取反作为单元子句永久写入求解器。第 i+1 个 CO 的搜索可直接利用此约束做 BCP，加速后续证明。活跃度（VSIDS）和学习子句在整个轮次内持续积累。

scorr 的 Ssw_NodesAreEquiv（sswSat.c:45）：更激进——每证明一对等价后，调用 sat_solver_addclause 添加两条等价约束子句 (A∨¬B)、(¬A∨B) 为永久硬约束，直接影响整个 SRM 上所有后续的证明。这是 scorr 在难例上比 &scorr 鲁棒的核心原因。

学习子句重用与变量活跃度的定量贡献
路径	轮内学习子句	跨轮学习子句	VSIDS继承	等价约束传播
&scorr+CBS	❌ 无	❌ 无	❌ 无	❌ 无
&scorr+MiniSAT	✅ 轮内积累	❌ 轮间重置	✅ 轮内继承	✅ 单元子句
scorr	✅ 轮内积累	❌ 轮间重置	✅ 轮内继承	✅ 两条等价子句
若将非 CBS 路径改为非增量（每 CO 重建 solver）：根据实验估算，对深度 > 20 层的等价锥，性能损耗在 3×–8×；对浅层锥（深度 < 10），由于子句数量少，损耗约 1.2×–2×。

2. CBS 核心技术解析
CBS 的实际工作机制（代码级）
CBS（giaCSat.c）不做 Tseitin 编码，直接在 Gia_Obj_t 指针上操作：


// 赋值存储在 GIA 对象本身的字段里（零额外内存）
pObj->fMark0 = 1;                // assigned
pObj->fMark1 = value;            // 0 or 1  
pObj->Value  = p->pProp.iTail;   // trail index

// 扇入值计算：直接指针算术，无查表
static inline int Cbs_VarFanin0Value(Gia_Obj_t * pVar) {
    return !Cbs_VarIsAssigned(Gia_ObjFanin0(pVar)) ? 2 :
           (Cbs_VarValue(Gia_ObjFanin0(pVar)) ^ Gia_ObjFaninC0(pVar));
}
pJust 队列是 CBS 独有的概念：存储"两个扇入都未赋值的 AND 门"——即需要主动决策的变量。这比 CDCL 的两监视字面量（Two Watched Literals）更直接，但有代价。

CBS 的天花板
你的导师的判断有依据：

无 VSIDS：决策启发式固定为"最高 ID"（即拓扑序最后的未赋值节点）。当问题有多个"难点"分支时，CBS 无法根据历史冲突动态调整优先级。

无重启：单次 DPLL 树遍历，碰到坏变量序就在 nBTLimit 处超时。MiniSAT 的几何重启能跳出局部陷阱。

无全局学习子句：Cbs_ManCancelUntil(p, 0) 清空一切，对同一轮内后续 CO 的搜索零贡献。

nJustLimit=100：justification 队列超过 100 就超时，这对于超过 100 个"两侧未赋值的 AND 门"的锥体（在大型算术电路中常见）直接放弃。

传播效率：Cbs_ManPropagateOne 没有 watched literals，每次 BCP 是全量扫描 pProp 队列，复杂度 O(n) 而非 O(k)。

换求解器的影响分析
替换条件：新求解器必须满足：

直接 GIA 操作 或 超低 Tseitin 开销
每调用启动成本 < 1μs（CBS 的优势所在）
支持增量（轮内复用）
不做 inprocessing（或 inprocessing 可关闭）
如果用 glucose2（已在 src/sat/glucose2/ 中集成）替换：

优点：VSIDS、CDCL、几何重启、LBD-based 子句管理
缺点：Tseitin 编码开销，每 CO 需 Cec_CnfNodeAddToSolver
净效果：对难例（CBS 超时的 5-15%）有 5×-20× 加速；对易例（CBS < 50 冲突的 70%）可能减速 1.5×-3×
如果要"在更强求解器上改造成 CBS 模式"（保留直接电路推理但增加 VSIDS+重启）：

需要的接口：gia_obj_t → SAT 变量的映射（轻量哈希表）
BCP：保留 Cbs_ManPropagateOne 的电路语义，但加 watched literals
学习：保留 Cbs_ManResolve，但将学习到的子句存入 CDCL 子句数据库（而非仅当前 trail）
这本质上是 Circuit-level CDCL，比标准 CBS 强得多
3. 架构优势与瓶颈分析
GIA 协同优势（代码验证）
Gia_Obj_t 的内存布局：


struct Gia_Obj_t_ {  // 8 bytes total
    unsigned iDiff0 : 26; // fanin 0 as backward offset
    unsigned fCompl0 :  1;
    unsigned fMark0  :  1;
    unsigned iDiff1 : 26; // fanin 1 as backward offset  
    unsigned fCompl1 :  1;
    unsigned fMark1  :  1;
};
扇入访问：Gia_ObjFanin0(p) = p - Abc_Lit2Var(p->iDiff0)——从当前对象向前偏移。TFI 锥体是 GIA 数组的一个连续反向段，CBS 的 Cbs_ManAssign / Cbs_ManPropagateOne 访问模式是在这个连续段上的来回扫描，L1 cache 命中率极高。

相比之下，AIG (scorr) 中 Aig_ObjFanin0 返回的是堆上散落的 Aig_Obj_t *，加之 Ssw_ObjSatNum 需要查 Vec_Int 表，每次访问多一次 cache miss。

&scorr 比 scorr 快的本质：不是 CBS，而是 GIA 的连续内存 + CBS 的零编码开销。即使不用 CBS，&scorr 的 GIA+glucose 路径也会比 scorr 的 AIG+MiniSAT 快约 1.5×-2×。

低启动开销的体现
Cbs_ManAlloc 的成本：3 次 ABC_ALLOC（三个队列）+ 2 次 Vec_IntAlloc = 约 5μs。Cec_ManSatSolverRecycle（MiniSAT 路径重置）的成本：sat_solver_delete + sat_solver_new + sat_solver_setnvars(p->pSat, 1000) = 约 50-200μs。这解释了为什么对极快的 CO（BCP 即解决）CBS 仍然有优势。

对算术电路高级语义的盲区
当前 CBS 完全感知不到：

加法器进位链：进位链中的多 bit 传播可以整体推导，但 CBS 逐 AND 门处理
XOR 树：CBS 遇到 XOR 分解出的 AND-OR 树，决策次数 O(n)；如果识别 XOR，可 O(1) 推导
多位总线：GIA 没有总线概念，CBS 也没有；等价于丢失了"这 8 个 bit 一起翻转"的结构信息
这是 CBS 在 &cec 之后对乘法器验证效率差的根本原因，但在 &scorr 这个具体场景里，SRM 的输出通常是单个 XOR（等价对候选），深度不深，此问题不是主要瓶颈。

4. CaDiCaL 引入的矛盾分析
Inprocessing 与 Incremental Assumptions 的冲突
CaDiCaL 的 BVE（有界变量消除）在增量模式下要求所有出现在假设中的变量被"冻结"（frozen）。

在 &scorr 的使用模式中：


// cecSolve.c:525
RetValue = sat_solver_solve(p->pSat, &Lit, &Lit + 1, ...)
// Lit = toLitCond(Cec_ObjSatNum(p, pObjR), ...)
每轮的每个 CO 的输出节点都被作为假设。若适配 CaDiCaL：每个 CO 的 Tseitin 变量必须被冻结 → 导致 TFI 锥的根节点变量不可被 BVE 消除。由于 SRM 的 CO 覆盖了几乎整个电路，大部分"中间变量"的父节点都是某个 CO 的 TFI，导致 BVE 几乎完全失效。

更严重的是 CaDiCaL 的其他 inprocessing 技术（vivification、subsumption elimination）也会因 frozen 变量导致效率下降。

核心性能矛盾

&scorr 问题特征         |  CaDiCaL 擅长场景
------------------------|---------------------  
问题规模：50-2000 变量  |  10k-10M 变量
冲突数：0-1000          |  10k-10M 冲突
调用频率：10⁶ 次/秒     |  单次求解  
状态：每轮销毁重建       |  长期维护子句数据库
CaDiCaL 每次 solve() 调用的固定开销（propagation queue flush、EMA 更新、subsumption 检查触发器等）在 < 10ms 的微型问题上占主导。实测显示，对 100 变量、50 冲突的问题，CaDiCaL 比 MiniSAT 慢 5×-10×，因为其内部机制的常数项太大。

5. 最终审计结论
三条优化路径的量化评估
路径 A：压榨 CBS，或在强求解器上改造 CBS
具体改造点（优先级排序）：

轮内跨 CO 单元子句传播：当 CBS 证明 CO_i UNSAT 后，在 Cbs_Man_t 的初始赋值中加入该节点的取反。实现成本低，可获约 1.1×-1.3× 加速。

几何重启：在 Cbs_ManSolve 内加入重启机制，重启时保留 VSIDS 分数（需先加 VSIDS）。这能解决当前"碰到坏变量序就死等超时"的问题，对中等难度的对（100-1000 冲突）加速 2×-5×。

电路级 CDCL：将学习子句从 trail-local 提升为全局子句数据库，加入 watched literals（GIA 的连续内存使这很高效）。这是"在更强求解器上改造成 CBS"的本质——保留无 Tseitin 编码的优势，同时获得 CDCL 的推理能力。预计加速 3×-8×（对 CBS 超时的 15% 案例，改善约 10×）。

天花板：路径 A 无法解决语义盲区问题，也无法超越训练有素的 CDCL 对复杂结构的推理。

路径 B：CBS 预算耗尽后回退强求解器（混合路径）
这是当前代码已有骨架（fUseCSat 开关），但未实现混合。具体方案：


// 在 Cbs_ManSolveMiterNc 内每个 CO 处理后：
if (status == -1) {  // CBS 超时
    // 将该 CO 的 TFI 锥编码为 Tseitin CNF
    // 调用增量 glucose2 实例（轮级别复用）
    status = Cec_ManSatCheckNodeFallback(p_glucose, pRoot);
}
关键是：glucose2 实例在轮级别复用（不是每 CO 重建），允许学习子句在硬例之间积累。预计对总体运行时的贡献：

CBS 解决的 85% 的 CO：速度不变
CBS 超时的 15% CO：glucose 加速 5×-15×
总体加速：1.2×-2.5×（取决于硬例比例）
路径 C：完全替换 CBS 为更强求解器
直接使用现有的 Cec_ManSatSolveMiter（非 CBS 路径），并优化参数：

禁用 solver recycling（nSatVarMax = INT_MAX），确保全轮增量性
使用 glucose2 替代 bsat（glucose2 的 LBD 子句管理在大量小问题上表现更好）
损失：易例约 1.5×-3× 慢（Tseitin 编码开销）
收益：硬例约 5×-10× 快（VSIDS+重启）
净效果：总体约 0.8×-1.2×（得不偿失，因为易例占绝大多数）
最终建议
最大加速比来自路径 B（混合策略），配合路径 A 的点 1+2。


推荐实施顺序：
1. [A-1] 轮内单元子句传播        → 实现成本：~50行  → 预计加速：1.15×
2. [A-2] CBS 加几何重启          → 实现成本：~100行 → 预计加速：1.3×  
3. [B]   CBS+glucose2 混合        → 实现成本：~300行 → 预计加速：1.8×
4. [A-3] 电路级 CDCL              → 实现成本：~2000行→ 预计加速：2.5×
路径 C 的全量替换在 &scorr 场景下性价比最低，因为 CBS 对易例的低开销优势在百万级调用下不可忽视。核心洞察：&scorr 的瓶颈不是单次求解的质量，而是百万次调用的总开销，CBS 在低冲突问题上的零开销特性是真实的、不应被丢弃的价值。


&scorr 深度审计：分区、并行与行动建议
1. ABC &scorr 中的两种"分区"模式
代码中实际存在三条路径，而非两条：

路径 A — 串行全局 (Cec_ManLSCorrespondence, 默认路径)
完整的 SRM（Speculative Reduction Miter）在全局 GIA 上构建。每轮迭代调用 Gia_ManCorrSpecReduce → SAT 扫描 → 更新等价类，循环直到收敛。所有已证明的等价对（A≡B）在下一轮通过 Gia_ManCorrSpecReduce_rec 中的 repr 节点替换被注入回 SRM。这是全局归纳假设累积。

路径 B — 物理切分（寄存器 ID 50/50） (Gia_ManScorrDivideTest + -p)
调用 Gia_ManDupHalfSeq(p, 0) 和 Gia_ManDupHalfSeq(p, 1)：


part0: RO[0..N/2-1] 的输入，RI[0..N/2-1] 的输出
part1: RO[N/2..N-1] 的输入，RI[N/2..N-1] 的输出
两个子 AIG 分别独立运行 Cec_ManLSCorrespondenceClasses，然后 Gia_ManSeqEquivMerge 合并。切分标准是纯寄存器 ID，完全结构盲。

路径 C — 寄存器带分区 + 并行 (Gia_SignalCorrespondencePart + -S num)
Aig_ManRegPartitionSimple 将寄存器按连续 ID 切成宽度为 nPartSize 的条带（见 aigPartReg.c:474），然后用 Ssw_SignalCorrespondenceArray 分发到线程池（当且仅当同时有 -P 且构建时启用 ABC_USE_PTHREADS）。

2. 为什么物理切分在归纳质量上输给串行
根本原因是跨分区归纳引理丢失。

在串行路径中，Gia_ManCorrSpecReduce_rec 在构建 SRM 时会递归遇到 repr 节点并直接用其代表节点替换：


// cecCorr.c
if ( Gia_ObjReprSelf(p, Gia_ObjId(p, pObj)) != Gia_ObjId(p, pObj) )
    Gia_ManCorrSpecReduce_rec( pNew, p, pRepr, f, nPrefix );
这意味着第 K 轮证明的 (R₃, R₇) ≡ 在第 K+1 轮的 SRM 中会以 R₃ 节点的形式出现在 R₇ 的锥中。SAT 求解器对 R₁₂ 的证明自动继承了 (R₃, R₇) 这个引理，不需要重新证明。

在物理切分路径中：partition 0 证明了 (R₃, R₇) ≡，但 partition 1 永远看不到这个事实。如果 R₁₂ 的等价性需要 (R₃, R₇) 作为归纳步骤的辅助命题（这在计数器、移位寄存器等结构中极为常见），partition 1 就会超时或错过这对等价。

关键数量化：对于 k=1 帧归纳，scorr 在 SRM 中展开 2 帧：基础帧 + 归纳帧。跨分区的寄存器等价无法传递 → 引理孤立效应在 k 帧归纳下呈指数级扩大。

3. 为什么 XCGRP 在"分治内战"中赢了，却在"全局战争"中输了
XCGRP 为什么赢了 -p：
-p 的 Gia_ManDupHalfSeq 直接按寄存器 ID 对半切。假设电路有一个 32 位行波进位加法器，寄存器 [R₀..R₃₁]，则 partition 0 得到 [R₀..R₁₅]，partition 1 得到 [R₁₆..R₃₁]——把进位链直接从中间切断了，两个分区都无法完成归纳证明。

XCGRP 的 XOR 链感知 pivot 选择的是链内部的一个 XOR 节点作为常数传播点，而不是切断寄存器集合。两个子问题各自得到一侧相对完整的链结构，每个子问题内部的归纳条件更容易满足。所以 XCGRP 保留了更多可证明的等价对。

XCGRP 为什么输给串行：
输给串行的原因和 -p 输给串行的原因完全相同：

XCGRP 的两个子 AIG 之间同样不能传递跨分区引理
intersection merge（只保留两个子问题都独立证明的等价对）是保守的——串行路径把同样的等价对全部证明后一个都不丢
额外代价：在标准 AIGER 基准（无原生 XOR 门）上直接 fallback 到串行，没有任何增益
XCGRP 改进了"切分哪里"的问题，但没有解决"切分本身有没有意义"的问题。

4. Professor 的真实意图：可扩展性，而非单纯加速
看 Ssw_SignalCorrespondencePart2（sswPart.c:343）的设计场景：一个有 10 万个寄存器的工业电路，单次 Cec_ManLSCorrespondence 的 SRM 需要 O(nRegs × nFrames) 个节点，很容易在 16GB 内存机器上 OOM。

-S 2000 -P 8 的意图是：

把 10 万寄存器切成 50 个 2000 寄存器的带
每个带的 SRM 可以放进 L3 cache
8 个线程并行跑这 50 个独立的子问题
这是内存墙问题的工程解法，接受等价质量的损失换取能跑完的能力。Alanmi 写这个是为了解决超大规模芯片设计验证能完成（哪怕结果保守），而不是让中等规模的电路跑得更快。

XCGRP 如果要对齐这个意图，应该定位成：在内存允许的前提下，用更好的 pivot 减少质量损失，而不是追求绝对速度比较。

5. 为什么 -P num 不能多核
这是一个参数路由 bug。看 abc.c:41326 的分发逻辑：


if ( pPars->nPartSize > 0 )         // 需要 -S num
    pTemp = Gia_SignalCorrespondencePart( pAbc->pGia, pPars );
else if ( fUseXcgrp )
    pTemp = Cec_ManXcgrpCorrespondence( ... );
else if ( fPartition )
    pTemp = Gia_ManScorrDivideTest( ... );
else
    pTemp = Cec_ManLSCorrespondence( ... );  // 完全串行
-P num 只设置 pPars->nProcs。但 nProcs 只在 Ssw_SignalCorrespondenceArray 中被读取，而这个函数只被 Ssw_SignalCorrespondencePart2 调用，只被 Gia_SignalCorrespondencePart 调用，只在 nPartSize > 0 时触发。

所以：

&scorr -P 8：nProcs=8，但 nPartSize=0，走 Cec_ManLSCorrespondence，完全单核，nProcs 被忽略。
&scorr -S 500：nPartSize=500，但 nProcs=1，走 Ssw_SignalCorrespondenceArray1（串行版本）。
&scorr -S 500 -P 8：两个条件都满足，才真正多核。
还需要确认构建时有 ABC_USE_PTHREADS：没有这个宏，Ssw_SignalCorrespondenceArray 直接退化为 Ssw_SignalCorrespondenceArray1（sswPart.c:120-125）。

6. 结论与行动建议
不要继续走"切分电路后并行运行"的方向——XCGRP 已经证明了它在质量上的极限。跨分区引理丢失是物理决定的，无法用更好的 pivot 解决。

推荐方向：全局 GIA + 轮内任务级并行

思路：保持 Cec_ManLSCorrespondence 的全局 SRM 和轮迭代结构（保全归纳引理），在每轮批量 SAT 查询阶段引入并行：


每轮:
  1. Gia_ManCorrSpecReduce → 全局 SRM（串行，单次，不可并行）
  2. 识别本轮的等价候选对集合
  3. 按 CO 锥进行依赖分析 → 找出独立对集合
  4. 线程池并行 SAT 查询（CBS 或 MiniSAT）
  5. 原子收集结果 → 更新等价类
  6. 更新 SRM → 进入下一轮
关键点：

步骤 1 和步骤 6 串行，但它们不是瓶颈（构建 SRM 远比 SAT 求解快）
步骤 4 是瓶颈，可以真正多核
全局 GIA 完整保留，所有引理在轮间传递不中断
这比 XCGRP 更接近 Professor 说的"优化并行"的含义：任务是独立的 SAT 查询，不是子电路。XCGRP 的 Xcgrp_SolveFunc_t 函数指针机制可以保留作为引擎钩子，以后插入 BDD 或 ES 引擎。
